HAMi 第三课：HAMi-core 原理拆解

分三段学习：启动配置如何交付 → 一次调用如何执行 → 并发、失败与证据如何追问。

这课要教会你：独立追踪一条 CUDA 显存调用，解释每个参与者的输入、状态变化、输出与故障边界。会算预算只是起点。

建议分三次学习，每次 10–15 分钟：先读准备链路，再读运行时和账本，最后做失败实验与工程追问。每段都要能回到源码定位。

基线：HAMi v2.7.0 / f754a8c；其 libvgpu 引用 HAMi-core 3506e62。它们是本课源码阅读基线，不是当前课程服务器的 GPU 部署版本。网页实验和调用轨迹均为教学模型。

逐步讲解

第一段 · 显存申请发生以前，谁已经做过什么？

把“运行一个 Pod”和“申请一次显存”分开看。前者建立配置，后者在应用进程内部执行。不能把所有组件画成每次调用都经过的串行链路。

1. Webhook：决定准入阶段怎样改写 Pod。

输入是 Pod 资源声明；输出包括满足处理条件时设置的 schedulerName。它不读取应用当前显存使用量，也不审批每次 cudaMalloc。

2. kube-scheduler + HAMi Extender：决定放在哪里。

输入包括 Pod 请求与设备状态，输出是节点、设备和预算的分配记录。调度层的预算是资源规划依据，不是已经分配的 CUDA 指针。

3. kubelet + HAMi device-plugin：准备容器能看见什么。

在本版本非 MIG 共享分支，插件读取分配注解，生成 CUDA_DEVICE_MEMORY_LIMIT_i、CUDA_DEVICE_SM_LIMIT 和共享缓存位置，挂载 libvgpu.so；默认控制分支还挂载 /etc/ld.so.preload。它把 AllocateResponse 交给 kubelet，由启动链路落实配置。

4. 容器加载器 + HAMi-core：把配置变成进程中的行为。

动态库必须真正进入目标进程，相关 CUDA 调用必须命中 Hook。宿主机有库、容器里有文件、环境变量存在，都不等于进程已经走了受控路径。这个版本不只依赖 LD_PRELOAD 环境变量，排查时还要看 /etc/ld.so.preload。

源码依据：设备插件 Allocate 的配置交付分支；运行库读取每设备限额与回退限额。

工程用途：超限仍成功时，先检查这条准备链路：请求是否被接管、设备分配是否匹配、预算和缓存是否交付、目标进程是否加载。不要直接从应用现象跳到“调度器坏了”。

第二段 · 一次显存申请，真正走过哪些函数？

现在假定容器准备正确、当前线程已有正确 CUDA context，只讨论同步 cuMemAlloc_v2。应用可以由 CUDA Runtime 或框架间接发起调用，本课从 Driver API Hook 入口展开；不把 async、memory pool、managed memory 视作完全相同路径。

打开源码关联的运行时图 ↗
  1. 截获入口：HAMi-core 的 cuMemAlloc_v2 包装函数进入 allocate_raw；它不是向调度器发送一次 RPC。见 cuMemAlloc_v2 → allocate_raw.
  2. 确定设备和限额：取当前 CUDA context 对应设备，读取该设备的逻辑 limit，汇总共享区域中记录的 usage。见 oom_check：读取 limit 与 usage 与 get_gpu_memory_usage：汇总共享区域.
  3. 检查：若 limit 非零且 usage + request 超限，返回 CUDA_ERROR_OUT_OF_MEMORY，不走真实显存分配分支。设备与 context 查询仍可能调用 Driver，不能泛化为“完全没有 Driver 调用”。limit 为 0 时该检查分支不施加此预算上限，所以还要核对配置解析结果。这里的量是账本口径，不等同于 nvidia-smi 的整卡数值。
  4. 调用底层：预算通过后调用真实分配函数。当前基线 add_chunk 的大小分支最终都可追到真实 cuMemAlloc_v2；预算许可不等于物理资源保证。
  5. 按返回值记账：底层失败则把错误返回，未进入成功记账分支；底层成功才登记地址、大小并更新使用量。见 add_chunk：先检查，再调用，成功才记账.
  6. 应用处理结果：得到成功指针才继续使用；失败后由应用或框架决定降负载、释放后重试、报错或退出。该同步申请路径本身并不等于 Kubernetes 自动重调度。
本课基线同步路径的简化伪代码（不是完整源码）
lock(process_local_mutex)
if tracked_usage + request > nonzero_limit:
    return OOM                # 不调用真实显存分配函数
result = real_driver_allocate(request)
if result != SUCCESS:
    return result             # 不登记成功分配
record_pointer_and_increment_usage()
return SUCCESS
# 各出口的解锁由 allocate_raw 包装层完成
把“拦截”再拆一层：为什么函数会先进入 HAMi-core？

预加载把 libvgpu.so 放进动态链接过程；同名 CUDA 包装符号先执行限制逻辑。本版本还包装 dlsym：对 cu 开头的符号尝试从 vgpu 库解析；cuGetProcAddress 也有包装路径，用于处理通过函数指针取得入口的调用。单说“LD_PRELOAD 一加就都受控”遗漏了符号解析方式与 API 覆盖。

进入包装函数后，库通过 cuda_library_entry 中保存的真实函数指针调用原始 Driver，而不是再按同名包装入口递归调用自己。CUDA_OVERRIDE_CALL 是这一层间接调用宏。这里仍是同一进程中的用户态函数调用；只有最终 Driver 操作才进入其设备管理路径，不是把请求发回 Kubernetes。

查源码：dlsym 包装、cuGetProcAddress 包装、真实函数指针调用宏。

进一步问：库加载了，但某个新 API 没有命中包装，会发生什么？答案需要对照该版本的符号表、调用方式和实际轨迹；不能拿 cuMemAlloc_v2 的结果覆盖所有 API。

为什么这样设计？把每次申请留在用户态调用路径，避免逐次依赖控制面往返；代价是正确性依赖加载、API 覆盖、设备编号、共享状态与版本实现。延迟收益要用基准测量，本课不提供没有测量的性能数字。

第三段 · 账本是谁的？释放以后改变了什么？

在该源码中，get_gpu_memory_usage 汇总共享区域内多个进程的记录，并含初始偏移；共享区域通过缓存文件 mmap。它不是浏览器传来的一个 used 参数，也不只是当前进程的一个普通变量。

插件生成共享缓存位置，意味着验证时必须问：哪些进程实际映射到同一份缓存？设备编号是否对应同一 GPU？两个容器是否真的共享同一预算域？不能因为同节点、同 GPU 就断言它们共用同一份运行时账本。

跟踪过的指针进入 cuMemFree_v2 → free_raw → remove_chunk 后，源码调用底层释放并扣减运行时记账。见 remove_chunk：释放并扣减使用量。但该旧版本 remove_chunk 未依据 cuMemoryFree 返回值决定是否扣账；正常路径能解释释放，异常路径仍必须实验验证，不能称为完备事务。

两本账不能混：运行时使用量下降，不代表 Pod 的调度预算已经释放。比如 Pod 仍申请 4 GiB，应用释放 2 GiB，只能说明运行时占用可能下降；该申请额度何时归还，要看 Pod 生命周期与调度层回收。强杀进程、缓存陈旧、框架保留池内存，也不能一概等同于一次正常 cuMemFree。

工程用途：解释“任务已释放内存，为什么别的任务还 Pending”，以及“进程已经退出，为什么账本仍显示使用”。先定位是哪本账，再找回收责任方。

第四段 · 两种失败看起来相同，处理方法却不同

预算侧拒绝：模型中 2 + 3 > 4，真实显存分配函数没被调用。应核对限额、账本、工作集与请求是否合理；单纯增加整卡空闲显存不一定解除逻辑限额。
底层分配失败：模型中 2 + 1 ≤ 4，真实显存分配函数被调用但失败。应检查物理资源、其他进程、设备或 context 状态与具体错误；只提高逻辑额度不一定有用。

同为 CUDA_ERROR_OUT_OF_MEMORY 不能单凭错误码归因。要关联 Hook 日志的 usage/limit/request、是否走到真实分配调用、Driver 返回值与独立设备观测。预算通过是必要检查之一，不能作为资源可用性的充分证据。对照 NVIDIA Driver API 内存管理定义。

第五段 · 顶尖工程师会追问：检查和记账之间，能插进另一个进程吗？

共同账本已用 2 GiB，A、B 两个进程各申请 1.5 GiB。若两者都在对方记账前读到 2 GiB，两次检查都会通过；若底层都成功，最终可能记到 5 GiB。读、写各自加锁，不等于“检查—调用—记账”整体原子。

本课基线 allocate_raw 的 mutex 是进程内互斥；共享账本的局部读写另有锁。由源码顺序可以提出上述跨进程交错反例，但本机没有执行上游 CUDA 并发复现，不能把推理冒充硬件实测。

继续向下追：怎么改，改完又会出现什么问题？

一个改法是在共享锁下完成检查与额度预留，再把昂贵的 Driver 调用移到锁外；底层失败时回滚预留。新的问题是：预留后崩溃怎么清理？回滚是否重复执行？设备编号是否映射正确？async 分配何时完成、何时记账？释放失败能否导致账实不符？

作为独立版本比较，较新提交的 reserve/release 与 分配失败回滚路径已经体现共享预留思路。它不是 v2.7.0 这条基线，不能由此认定所有版本或所有 API 均解决了并发问题。

第七段 · 除了我们口头解释，靠什么核对？

  1. 固定材料：记录本课两个提交、实际镜像摘要与运行环境；验证 HAMi 的 libvgpu gitlink，不能用“都是 main”代替配套关系。
  2. 静态核对：沿入口、调用者、错误分支、记账点和释放点读取源码，区分已读到的事实与待实验的推断。
  3. 模型核对：从 ReplaceU 克隆后运行 projects/hami-memory-lab 的测试，重建轨迹，检查“拒绝不调用真实分配函数、失败不新增成功记账、相同错误码不同根因”等不变量。通过只证明模型自洽。
  4. 真实验证：有匹配 NVIDIA 环境后运行仓库里的 CUDA 探针；比较加载/未加载、预算内/超预算、释放后再申请，并关联进程 maps、缓存位置、日志和设备指标。并发与崩溃另列实验，不凭同步探针代替。
  5. 独立复现：保留程序、命令、版本与原始输出，交给另一人从空环境执行。输出分“通过、失败、不确定”，缺硬件就保留待验证。

第八段 · 开放追问：能解释到哪一层？

  1. 调度器已经分配 4 GiB，为什么每次申请还要检查？如果调度器暂不可达，这条本地同步调用链本身是否需要向它发 RPC？
  2. limit 从哪来，usage 从哪来？为什么让应用自己报告 used 会失去隔离意义？
  3. 两次都报 OOM，怎样证明一次没进入真实分配，另一次进入后失败？
  4. 应用 free 了 2 GiB，为什么平台不能立刻把这 2 GiB 当成未申请资源分给别的 Pod？
  5. 多个进程怎样共同遵守一个限额？为什么一个 pthread_mutex 不自动解决跨进程竞态？
  6. 如果进程在底层成功、账本更新前崩溃，如何发现账实差异？需要什么补偿或清理机制？
  7. 如果改用 async、memory pool、不同设备编号或新版本，现有结论哪些必须重新核对？

先选一个问题，用“参与者 → 状态 → 分支 → 证据 → 用途”五步讲给我。遇到不清楚的函数直接回对话问我，我们沿那条路径继续拆。
