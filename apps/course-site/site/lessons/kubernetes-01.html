Pod 创建请求怎样找到处理入口？

旅程坐标

起点：客户端发起 Pod 创建请求 → 本课：服务器注册路由、请求到达创建处理器 → 下一课：请求信息、认证与授权如何参与。

闭环问题

一条 POST /api/v1/namespaces/default/pods 请求，为什么最终会进入通用创建处理器，而不是直接调用 Pod 存储？

一、先分清两条时间线

服务启动时，API Server 根据资源存储能力注册路由；请求到达时，HTTP 过滤器和路由把请求交给已注册的处理器。下面只展示本课需要的片段；创建成功和写入 etcd 属于后续步骤。

沿用本课场景：客户端准备创建 default 命名空间中的 Pod。以下只展示与本课有关的调用；图谱关系经过 Kubernetes v1.28.0 源码复核，分支假设均为示例。

每一步把什么交给下一步？启用 Pod 资源时，NewRESTStorage 把 Pod 的存储实现放入资源映射；随后安装逻辑读取该映射，为资源注册 POST 处理函数。restfulCreateResource 在启动时返回一个闭包，路由持有它；此时尚未处理任何 Pod 请求。

把“交给下一步”拆开看

假设 Pod 资源已启用，稍后客户端会向 default 命名空间创建 Pod。先看启动阶段准备了什么。

① 准备 Pod 的存储实现。 legacyProvider.NewRESTStorage 创建 Pod 存储对象，并在资源启用时放入映射：

podStorage, err := podstore.NewStorage(...)
// 检查 err；确认 pods 资源已启用后：
storage["pods"] = podStorage.Pod

映射把资源名 "pods" 和对应存储实现关联起来。它交给后续安装流程的是资源名到存储实现的对应关系；此时没有创建 Pod。源码：pkg/registry/core/rest/storage_core.go:190, 212, 226–227。

② 根据存储实现安装路由。安装逻辑遍历资源映射，把资源名和相应存储实现传给 registerResourceHandlers。当该实现支持创建操作时，安装逻辑准备 POST 路由。对于命名空间中的 Pod，请求路径形如 /api/v1/namespaces/{namespace}/pods。源码：staging/src/k8s.io/apiserver/pkg/endpoints/installer.go:199–205, 896–910。

③ 构造处理函数并保存。普通创建分支调用：

handler = restfulCreateResource(creater, reqScope, admit)
handler = metrics.InstrumentRouteFunc(...) // 指标包装，节选
handler = utilwarning.AddWarningsHandler(handler, warnings)
route := ws.POST(action.Path).To(handler)

上面是按源码顺序展示的节选，省略了包装器的参数。creater 提供创建资源的能力；reqScope 保存请求处理所需的信息；admit 提供准入处理能力。它们被传给 restfulCreateResource：

func restfulCreateResource(r rest.Creater, scope handlers.RequestScope,
    admit admission.Interface) restful.RouteFunction {
    return func(req *restful.Request, res *restful.Response) {
        handlers.CreateResource(r, &scope, admit)(res.ResponseWriter, req.Request)
    }
}

return func(...) 返回的是一个函数；它记住了 r、scope 和 admit，因此叫闭包。启动时先构造闭包、经过包装后绑定到路由；函数体里的创建处理此时尚未执行。源码：staging/src/k8s.io/apiserver/pkg/endpoints/installer.go:901–910, 1278–1281。

④ 请求到达后再执行。例如 POST /api/v1/namespaces/default/pods 通过前置处理并匹配路由后，路由调用已保存的处理函数。闭包才调用 handlers.CreateResource 并立即执行返回的处理函数，随后读取、解码请求体，进入后续准入与创建流程；这些步骤中的错误可能使请求提前结束。

串起来：Pod 存储实现 → 资源映射 → 路由安装逻辑 → 绑定处理函数 → 等待请求 → 匹配后执行。前三步发生在启动时，最后一步发生在请求到达时。

路径对应：pkg/controlplane/instance.go；pkg/registry/core/rest/storage_core.go；其余文件分别位于 staging/src/k8s.io/apiserver/pkg/server/genericapiserver.go、.../endpoints/groupversion.go、.../endpoints/installer.go。

第二段：请求到达后执行闭包

POST /api/v1/namespaces/default/pods
  → API Server 的过滤器链与路由匹配
  → restfulCreateResource 返回的闭包        installer.go:1278–1280
  → handlers.CreateResource(...)             installer.go:1280
  → createHandler(..., false)               create.go:244–245
  → 执行返回的 HTTP 处理函数               create.go:53–54
  → 读取请求体                              create.go:93
  → decoder.Decode(...)                     create.go:124–126
  → 条件成立时执行变更准入 Admit             create.go:201–204
  → requestFunc() → r.Create(...)           create.go:182–189, 208

衔接关键：路由匹配成功后，才执行启动阶段保存的闭包；闭包调用 CreateResource 并立即执行它返回的处理函数。解码得到的对象随后被传入准入和存储创建流程。准入是否执行取决于配置及接口判断；读取、解码或准入报错会提前返回，不能把调用 r.Create 当作已经成功写入。

installer.go 的完整路径见上；create.go 位于 staging/src/k8s.io/apiserver/pkg/endpoints/handlers/create.go。上图及链条省略了部分包装器、错误处理和其他资源分支。

二、启动时：Pod 存储如何变成 POST 路由？

源码 pkg/registry/core/rest/storage_core.go:190、:226

podStorage, err := podstore.NewStorage(...)
// 省略错误处理和其他资源
if resource := "pods"; apiResourceConfigSource.ResourceEnabled(...) {
    storage[resource] = podStorage.Pod
}

这里先构造 Pod 存储；当 Pod 资源启用时，把它放到资源存储表的 pods 项。这发生在服务初始化过程，不是收到每个 Pod 请求时重新创建。

源码 staging/src/k8s.io/apiserver/pkg/endpoints/installer.go:190、:205、:543、:567、:896

for _, path := range paths {
    apiResource, resourceInfo, err :=
        a.registerResourceHandlers(path, a.group.Storage[path], ws)
    // 省略后续处理
}
// registerResourceHandlers 内：
actions = appendIf(actions, action{"POST", resourcePath, ...}, isCreater)
// 后续按 POST action 生成路由
handler = restfulCreateResource(creater, reqScope, admit)
route := ws.POST(action.Path).To(handler)

上一步的资源存储进入 API 组的存储表；安装器遍历表，根据存储实现支持的接口生成操作。对于命名空间作用域的可创建资源，构造 POST 路径，随后把路由绑定到对应处理器。省略号代表摘录，不是可直接编译的原始代码。

三、请求时：闭包怎样接过请求？

源码 staging/src/k8s.io/apiserver/pkg/endpoints/installer.go:1278

func restfulCreateResource(r rest.Creater, scope handlers.RequestScope,
    admit admission.Interface) restful.RouteFunction {
    return func(req *restful.Request, res *restful.Response) {
        handlers.CreateResource(r, &scope, admit)(res.ResponseWriter, req.Request)
    }
}

关联：注册路由时调用 restfulCreateResource，得到并保存闭包；请求命中路由时才执行闭包，调用 handlers.CreateResource。r 是注册时捕获的创建接口，req 是当前 HTTP 请求。

源码 staging/src/k8s.io/apiserver/pkg/endpoints/handlers/create.go:244、:53、:93、:124

func CreateResource(r rest.Creater, scope *RequestScope,
    admission admission.Interface) http.HandlerFunc {
    return createHandler(&namedCreaterAdapter{r}, scope, admission, false)
}
// createHandler 返回的函数中：
body, err := limitedReadBodyWithRecordMetric(...)
obj, gvk, err := decoder.Decode(body, &defaultGVK, original)

通用处理器取得请求体并解码为资源对象；错误会沿对应分支返回。后面的准入、存储和响应尚未在这一课展开。进入处理器不等于 Pod 已创建成功。

四、请求进入路由前还经过什么？

staging/src/k8s.io/apiserver/pkg/server/config.go:906、:910、:937、:966 展示了默认过滤器链的构造。包装顺序和请求执行方向相反；请求信息、认证和授权等会在到达内部处理器前参与，具体链条与配置将在下一课逐段追踪。

跨课联系

这里先注册处理器、之后由事件触发的思路，与后面 kubelet 注册事件处理并响应 Pod 变化有相似的组织方式；两者的输入和运行机制不同，不是同一条调用链。

术语表

REST 存储：资源操作的服务端实现。路由：HTTP 方法和路径与处理函数的绑定。闭包：携带创建时捕获变量的函数值。
