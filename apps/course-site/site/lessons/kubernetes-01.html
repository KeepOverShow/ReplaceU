逐步讲解

学完能回答：Pod 为什么还在 Pending？调度器怎样从两个节点中选出一个？选中后是否已经完成绑定？

从一个例子出发

假设 Pod gpu-demo 请求 1 核 CPU 和 2 GiB 内存。节点 node-p4 剩余可调度 CPU 为 2 核，node-b 为 0.5 核。这里是便于讲解的假设，不代表实际集群测量值。先忽略 GPU 与其他约束。

第一步：先拿到调度缓存的快照

源码：Kubernetes v1.28.11，pkg/scheduler/schedule_one.go，schedulePod。

if err := sched.Cache.UpdateSnapshot(...); err != nil {
    return result, err
}
feasibleNodes, diagnosis, err :=
    sched.findNodesThatFitPod(ctx, fwk, state, pod)

解析：先把调度器缓存更新为本轮使用的节点快照，再把 Pod 和快照交给筛选过程。快照不是实时读取每台机器；失败会直接结束这次调度。下一步需要判断快照中哪些节点满足要求。

第二步：PreFilter 准备，Filter 逐节点筛选

源码：同一文件，findNodesThatFitPod 与 findNodesThatPassFilters。

preRes, s := fwk.RunPreFilterPlugins(ctx, state, pod)
// ...
nodeInfo := nodes[(sched.nextStartNodeIndex+i)%numAllNodes]
status := fwk.RunFilterPluginsWithNominatedPods(
    ctx, state, pod, nodeInfo)

解析：PreFilter 处理适用于整个 Pod 的准备工作，也可返回候选节点集合；Filter 在每个候选节点上运行。nodeInfo 是节点及已知 Pod 等信息的调度器视图，status 是本次筛选状态。并非每个插件都会启用，具体取决于调度配置。

代入断点：当 nodeInfo.Node().Name == "node-p4"，假设所有已启用筛选插件都通过，则 status.IsSuccess() == true，该节点进入可行节点集合。对 node-b，如果 NodeResourcesFit 因 CPU 不足拒绝，则结果为不可调度；这里描述的是假设的插件结果，不是实测日志。

与下一步的关系：只有通过 Filter 的节点参与后续决策；筛选后没有节点时，会返回 FitError，可能进入 PostFilter 尝试抢占。

第三步：候选不止一个才需要比较

if len(feasibleNodes) == 1 {
    return ScheduleResult{SuggestedHost: feasibleNodes[0].Name, ...}, nil
}
priorityList, err := prioritizeNodes(..., feasibleNodes)

解析：上一步只剩 node-p4，所以直接返回该节点；不能说本例经过了 Score。若有多个可行节点，才调用打分流程；各插件得分结合配置权重，最高分节点被选出。若存在 extender，还可能加入其优先级结果。

第四步：选中、假定、绑定不是一回事

源码：同一文件，schedulingCycle 与 ScheduleOne。

err = sched.assume(logger, assumedPod, scheduleResult.SuggestedHost)
if sts := fwk.RunReservePluginsReserve(ctx, state, assumedPod,
    scheduleResult.SuggestedHost); !sts.IsSuccess() {
    fwk.RunReservePluginsUnreserve(ctx, state, assumedPod, ...)
    sched.Cache.ForgetPod(logger, assumedPod)
}

解析：选出节点后，Assume 在调度器缓存里先记下这个 Pod；Reserve 给已启用插件预留资源。Reserve 失败时执行 Unreserve 并撤销缓存假定。成功还要经过 Permit 等步骤，然后才进入异步绑定周期；假定成功不等于 API Server 已确认绑定。

关联 HAMi：当调度器配置了 HAMi extender 且请求符合其参与条件，原生筛选、外部筛选与绑定按配置衔接。HAMi 的外部接口不等同于原生 framework 插件，详见 HAMi 第二课。

如何验证

kubectl get pod gpu-demo -o wide
kubectl describe pod gpu-demo
kubectl get pod gpu-demo -o jsonpath='{.spec.schedulerName} {.spec.nodeName}'

先看实际调度器名称、nodeName 和事件，再根据失败插件与原因查对应日志；空 nodeName 不能单独证明是哪一环失败。调度完成也不代表容器已经启动成功。
