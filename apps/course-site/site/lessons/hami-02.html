逐步讲解

HAMi 用于 Kubernetes 异构设备管理与共享。今天用一个服务申请 4 GiB 显存的例子，只看它如何从请求走到运行。HAMi 是完整项目，HAMi-core 是其中的容器内运行库。

先认两个名字：Webhook 是 Pod 准入时检查、改写配置的入口；Extender 是调度器调用的扩展服务。它们都不负责检查应用每一次显存申请。

1 · 先学会分开两个问题

调度分配：任务放到哪个节点、哪张卡，预留多少预算？运行约束：应用实际申请资源时，限制是否起作用？前一个问题有答案，不会自动回答后一个。

依据：HAMi v2.7.0 官方架构说明。这里固定的是课程阅读版本，不表示当前环境部署了该版本。

2 · 沿图走，每一站只问一件事

① 请求 → ② Webhook

负责：识别请求，按配置设置调度入口。

查证：提交前后 Pod YAML、schedulerName、准入配置。

③ 调度器与 Extender

负责：选择节点与设备。

查证：Pod 分配记录、Events、相同 Pod 的调度日志。

④ 节点设备插件

负责：参与设备与配置交付。

查证：节点分配日志、容器启动配置。

⑤ HAMi-core → ⑥ Driver/GPU

负责：在支持路径中检查应用使用。

查证：目标进程加载记录、实际 CUDA 调用及设备观测。

图中合并了 API Server、kubelet 和容器启动链路，箭头表示职责顺序，不表示组件彼此直接调用。HAMi-core 是用户态库；图中⑤必须满足“正确加载且调用路径受支持”。

3 · 三类证据，结论逐级收窄

配置：声明了限制意图。分配：记录了设备与预算。运行：在指定环境与调用路径下观察到限制效果。加载记录只是运行验证的必要线索之一，单独看到库名仍不够。

即使一次超额申请失败，也可能是物理显存不足、设备错误或别的限制。必须排除其他原因，才能把结果归因到 HAMi-core。

4 · 对照练习：先判断，再揭示

下面是合成证据卡，用于练习推理，不是这台机器的执行日志。A、B 假定使用同一卡、同一程序与镜像、相同申请序列和空闲条件，只改变受支持路径中运行库是否生效。

配置预算：4096 MiB；先申请 2048 MiB，再申请 3072 MiB。
A：分配记录存在；运行库未加载；两次申请均成功。
B：分配记录存在；运行库已加载；第二次被预算检查拒绝。
只看 A 的分配记录，能否宣称限制生效？

再看 C：库已加载，第二次申请失败，但没有记录失败原因和设备空闲情况。

C 是否足以证明 HAMi-core 拒绝了超限申请？

5 · 从什么原始材料开始查

先读上方固定版本架构页，找到四类职责；再读 HAMi-core 官方源码与测试，区分 CUDA 调用拦截与设备分配。该仓库默认分支会变化，实验时须另记 commit 和镜像摘要，不能把阅读版本当作运行版本。

进阶：有真实 NVIDIA 环境后，怎样让别人复现？
  1. 固定环境：记录 Kubernetes、HAMi、HAMi-core 的版本或 commit、镜像摘要、驱动、GPU 型号、运行时与完整配置。
  2. 做预算内正例：同一小程序先申请 2 GiB，检查返回值并实际使用内存，保存原始输出。
  3. 做超预算反例：保留第一次申请，再申请 3 GiB；结合库诊断与设备状态查明拒绝来源。
  4. 做运行库对照：在隔离的专用测试环境改变加载条件，其余保持一致；记录控制组是否有足够物理余量。缺少可比条件时标记“不确定”。
  5. 交叉验证与清理：关联同一 Pod UID、进程、时间与 GPU UUID 的配置、日志和设备指标；指标口径不必精确等于申请字节数。退出后检查资源回收。
  6. 交给第三人：提供程序、命令、配置、原始结果与判定标准，由其从干净环境复现。

本课没有执行上述硬件实验，不提供虚构的通过结论。用户态预算限制也不等于硬件分区或安全沙箱。
