VisitDevices 到底怎样遍历？

调用入口：NewDeviceMap() 把 NVML 包装成 device.Interface；buildGPUDeviceMap() 把一个 func(i int, gpu device.Device) error 传给 VisitDevices。i 是 NVML 设备索引，gpu 是该设备的操作句柄。

从硬件到 Node 资源：这些名词各指什么？

PCIe 设备：显卡接在主机上的硬件。Linux 能在硬件总线上发现它，说明“机器看到了卡”，还不等于 CUDA 可用。

NVIDIA 驱动与设备文件：驱动让系统能操作显卡；/dev/nvidia0、/dev/nvidiactl 等设备文件是程序访问驱动的入口。驱动未正常加载时，能看到 PCIe 设备也可能无法使用 GPU。

NVML：NVIDIA Management Library，供用户态程序查询 GPU 型号、ID、健康等信息的库。nvidia-smi 使用这类管理接口；HAMi 的设备插件也借它枚举本机 GPU。

Device Plugin：运行在节点上的进程，把本机设备转换成 kubelet 能识别的设备 ID。此处的 VisitDevices() 正在枚举硬件，GetName() 读取型号；还没有把资源写进 Node。

注册与设备列表：插件先向 kubelet 注册资源名和自己的 socket；kubelet 再调用 ListAndWatch 接收设备 ID 与健康状态。后续 kubelet 才据此计算并上报 Node.status.capacity、allocatable。

记忆顺序：Linux 发现卡 → 驱动可访问 → NVML 可查询 → 插件枚举并上报 → kubelet 更新 Node 资源。

那 kubectl describe node 的 Allocated resources 为什么会变？

假设这个 Pod 请求并限制 1 个同名 GPU 资源：Node.status.allocatable 仍为 2；describe node 的 Allocated resources 中，该资源的 Requests 和 Limits 会显示 1。这一栏由 kubectl 汇总该节点上未结束 Pod 的资源请求与限制，不是 Node.status 的 allocated 字段，也不是 kubelet 的设备 ID 分配表。

staging/src/k8s.io/kubectl/pkg/describe/describe.go
describeNodeResource()：调用 getPodsTotalRequestsAndLimits()，再输出扩展资源的 Requests、Limits。

所以要分别查：Node.status.allocatable 看上限；describe node 的 Allocated resources 看 Pod 请求汇总；kubelet 的 allocatedDevices 看实际占用的设备 ID。GPU 扩展资源的 describe 输出通常是 Requests=1、Limits=1，不会直接显示“1/2”。
