逐步讲解

1 · 从硬件开始：为什么装了显卡，Kubernetes 仍看不到？

先设想一台 Linux 节点插了两张 NVIDIA GPU。操作系统通过 PCIe 枚举发现设备；驱动绑定设备并提供访问接口，常见设备文件如 /dev/nvidia0、/dev/nvidiactl。NVML 是 NVIDIA 的用户态管理库，插件可借它枚举设备、读取 UUID、型号并监测健康信息。nvidia-smi 也是驱动管理能力的使用者。

这只解决了“这台主机能访问 GPU”。kubelet 不内置每家加速卡的枚举和健康检测逻辑；kube-scheduler 更不会通过 SSH 登录节点扫描 PCIe。需要厂商插件把硬件翻译成 Kubernetes 理解的资源。设备文件存在、nvidia-smi 成功、Node 有 GPU 资源、容器能运行 CUDA，是四层不同证据。

Device Plugin 是节点上的进程，通常用 DaemonSet 部署到 GPU 节点。它发现设备并实现标准 gRPC 服务；kubelet 内的 Device Manager 是消费者。NVML 不是 Kubernetes gRPC 协议，也不是调度器。

2 · 两个 Unix Socket，双方都当过客户端

gRPC 把“调用远端方法”变成结构化请求与响应，Protobuf 定义方法和消息字段。本课的传统 Linux Device Plugin API 经本机 Unix Domain Socket 通信：地址是文件路径，不需要给插件创建 Kubernetes Service，也没有通过 API Server 转发这些 RPC。

kubelet 的服务端：
  /var/lib/kubelet/device-plugins/kubelet.sock
  提供 v1beta1.Registration/Register

插件自己的服务端（示例名称）：
  /var/lib/kubelet/device-plugins/example-gpu.sock
  提供 v1beta1.DevicePlugin/*

插件先启动自己的 gRPC 服务，再连接 kubelet.sock 注册。Register 的 endpoint 填插件 socket 的文件名；kubelet 用该入口反向连接插件。目录通常通过 hostPath 共享给插件容器。路径相同不代表双方是同一个进程；文件存在也不保证服务仍能响应。

读主图时只盯箭头：Register 是插件 → kubelet；ListAndWatch 和 Allocate 是 kubelet → 插件。ListAndWatch 建立后，插件沿这个已打开的响应流发送更新，不是每次主动发起新的 Register。

3 · Register：报入口，不报设备清单

// 教学摘录，省略 import 与代码生成选项
service Registration {
  rpc Register(RegisterRequest) returns (Empty);
}
message RegisterRequest {
  string version = 1;
  string endpoint = 2;
  string resource_name = 3;
  DevicePluginOptions options = 4;
}

把一次请求写成易读的伪 JSON（实际线上是 Protobuf 二进制，不是 HTTP JSON）：

{
  "version": "v1beta1",
  "endpoint": "example-gpu.sock",
  "resource_name": "nvidia.com/gpu",
  "options": {
    "pre_start_required": false,
    "get_preferred_allocation_available": false
  }
}

version 是 Device Plugin API 版本，不是 Kubernetes 集群版本或 CUDA 版本。endpoint 告诉 kubelet 去哪里调用插件。resource_name 是 Pod 与 Node 使用的扩展资源键，kubelet 不会根据这个字符串自动加载 NVIDIA 驱动。options 告诉 kubelet 是否需要可选调用。

成功返回 Empty 只意味着注册 RPC 成功，返回中没有 GPU 数量，更没有 UUID 清单。若协议版本不兼容或入口不可达，先排注册链路；此时去调 Pod 的 gpumem 没有解决根因。

4 · ListAndWatch：一次请求，持续返回完整列表

service DevicePlugin {
  rpc ListAndWatch(Empty) returns (stream ListAndWatchResponse);
}
message ListAndWatchResponse { repeated Device devices = 1; }
message Device {
  string ID = 1;
  string health = 2;
  TopologyInfo topology = 3;
}

关键字 stream 在 returns 一侧：这是服务端流式 RPC。kubelet 发一次 Empty，插件先报告设备列表；设备健康或存在状态变化时，再在同一条流上报告更新后的列表。不是每帧只发送变动设备，也不是固定每秒查询一次。

第 1 帧（示例）：
  GPU-A Healthy，GPU-B Healthy
第 2 帧（GPU-B 故障，仍被报告）：
  GPU-A Healthy，GPU-B Unhealthy

ID 是插件定义的唯一标识，完整 GPU 场景常用 UUID；不要把示例 GPU-A 当真实 UUID。health 是 Healthy/Unhealthy；可选 topology 表示 NUMA 信息，不是显存大小或整套 NVLink 拓扑。标准 Device 消息没有“显存剩余多少”“核心比例多少”字段，这个缺口后面解释 HAMi 为什么要额外维护库存。

若流中断，设备清单不会凭空保持可信。要查插件进程、socket 和重连/重新注册；kubelet 重启后，插件需要重新注册。HAMi v2.7.0 此处会先 Send 初始列表，健康事件分支再标记 Unhealthy 并 Send；该实现还留有健康恢复的 FIXME，不能把协议允许更新理解为该版本自动恢复一切状态。

5 · kubelet 如何把设备列表变成 Node 资源

Device Manager 按 resourceName 管理设备与健康集合。固定 Kubernetes v1.31.10 的 GetCapacity 中，健康设备计入 capacity 和 allocatable，不健康设备只计入 capacity；节点状态构造逻辑把这些计数写入 Node，随后由 kubelet 发布给 API Server。以下假定插件一直连接，且故障设备仍保留在报告列表中：

两张健康设备：
status:
  capacity:    { nvidia.com/gpu: "2" }
  allocatable: { nvidia.com/gpu: "2" }

GPU-B 被报告为 Unhealthy 后：
status:
  capacity:    { nvidia.com/gpu: "2" }
  allocatable: { nvidia.com/gpu: "1" }

allocatable 不是当前空闲数。两张卡都健康时，即使一个 Pod 已申请 1 个资源，Node.allocatable 通常仍为 2。调度器还要结合已有 Pod 的请求占用判断剩余可调度量；kubelet 则另记具体设备分配。不要把“健康总量”“已申请数量”“物理显存使用量”混成一本账。

如果插件将设备从列表删除，或端点失效经过清理，capacity 的变化会不同；上面的 2→1 例子只针对“仍在列表中的不健康设备”。已有 Pod 也不会因为这个健康标志自动迁移到另一张卡。

两张卡健康，一个 Pod 申请 1 个资源后，Node.allocatable 是多少？

6 · Pod 来了：先选节点，再分配节点上的设备

# 标准完整 GPU 教学示例；本段尚未开启 HAMi 共享
resources:
  limits:
    nvidia.com/gpu: 1

扩展资源使用整数数量；只写 limits 时，Kubernetes 会把对应 request 补成相同值。调度器读取 Node 可分配资源及已有请求，结合污点、亲和性等约束选择节点，然后绑定 Pod。标准路径中，调度器通常不在 PodSpec 写入某个 GPU UUID。

节点 kubelet 在 Pod 准入/容器准备阶段，由 Device Manager 选择可用设备 ID，考虑已分配设备、拓扑和可选偏好，再调用插件 Allocate。它不是等应用第一次调用 CUDA 时才分配，也不意味着每次容器重启一定重新发同一 RPC；分配记录和缓存响应会影响复用。

rpc Allocate(AllocateRequest) returns (AllocateResponse);

// 便于阅读的请求示例：一个容器要使用 GPU-A
{ "container_requests": [{ "devices_ids": ["GPU-A"] }] }

这条标准请求没有 Pod 名称、命名空间、UID，也没有 4 GiB 显存预算。它按容器分组传入设备 ID。插件接收后执行设备相关准备并返回启动所需配置。正因为标准消息不携带上述信息，HAMi 才需要额外交接机制，不能凭想象给 AllocateRequest 加字段。

7 · AllocateResponse：把“选中了”变成“容器能接入”

响应中的 ContainerAllocateResponse 提供这些可选字段，不要求每种策略全部填写：

  • envs：容器环境变量，例如设备可见性配置；只写变量不等于运行时必然实现设备隔离。
  • mounts：宿主机文件/目录到容器路径的挂载，例如驱动库或插件运行库。
  • devices：设备节点的 host_path、container_path 与 r/w/m 权限。
  • annotations：交给容器运行时的注解，不是自动修改 Kubernetes Pod.metadata.annotations。
  • cdi_devices：CDI 设备标识；能否使用取决于 Kubernetes、运行时版本和配置。

kubelet 将响应融入容器配置，通过 CRI 交给容器运行时；运行时与 NVIDIA 接入组件按所选策略完成设备和驱动能力接入。插件不创建业务容器，Allocate 也不等于 cuMemAlloc。应用开始计算后，还要经过 CUDA 用户态库、驱动和硬件。

所以必须逐级验证：资源已上报 → Pod 已绑定 → Allocate 成功 → 配置被运行时消费 → 实际 CUDA 执行成功。最后一步不能靠 sleep 容器 Running 代替。

8 · 六个 RPC，一张职责表

RPC调用方向 / 类型作用与条件
Register插件 → kubelet / unary报版本、端点、资源名与能力
GetDevicePluginOptionskubelet → 插件 / unary读取插件可选能力
ListAndWatchkubelet → 插件 / server streaming持续接收设备完整列表
GetPreferredAllocationkubelet → 插件 / unary仅能力声明支持时请求偏好；建议不保证最终采用
Allocatekubelet → 插件 / unary根据设备 ID 返回容器接入配置
PreStartContainerkubelet → 插件 / unary仅声明需要时在启动前调用，可用于设备初始化

unary 表示一次请求对应一次响应。不要把可选 RPC 画成每次必经步骤。这个 API 也没有 Deallocate RPC；清理、设备占用记录与 Pod 生命周期关联，插件需要的清理机制不能假设由一个不存在的远程方法完成。

10 · 现在再接入 HAMi：标准协议缺了什么

前面先按完整 GPU 的标准设备插件讲清基础。HAMi 仍遵守 Device Plugin API，但共享模式改变了“上报一个设备 ID”的含义：v2.7.0 非 MIG 的 GetPluginDevices 会按 DeviceSplitCount 给每张物理卡生成多个带后缀的 ID。因此 Node 上的 nvidia.com/gpu 数量可能表示共享槽位，不能直接当物理卡数。

标准 Device 消息没有显存预算和核心份额，也不能表达“两个共享槽位最终落在同一张物理卡是否放得下”。HAMi 额外把实际 GPU 容量、UUID 等登记到节点注解，调度侧据此选择实际设备和预算，并把决定写入 Pod 注解。节点插件在非 MIG Allocate 分支通过 GetPendingPod、GetNextDeviceRequest 读取交接结果，核对设备数量，再生成库、预算和共享缓存等配置。

这里有两个必须区分的 ID：kubelet 管理的插件设备 ID，与 HAMi 选择的实际 GPU 身份。标准 Allocate 请求没传 Pod UID，HAMi 就需要额外的待分配 Pod 查找、阶段和锁来协调。具体怎样匹配、超时如何重试，是沿源码进一步追问的重点。

11 · 先把“一张卡”说清楚

本课要教会你从一个 Pod 请求，追到选中的 GPU 和容器启动配置，并定位交接在哪一步中断。传统 HAMi NVIDIA 共享路径中，nvidia.com/gpu: 1 指请求一张物理 GPU 上的使用份额；是否独占要结合共享配置与预算。它既不是“自动拿走整张卡”，也不是创建一张新的物理卡。

apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  containers:
  - name: ubuntu-container
    image: ubuntu:22.04
    command: ["bash", "-c", "sleep 86400"]
    resources:
      limits:
        nvidia.com/gpu: 1
        nvidia.com/gpumem: 3000
        nvidia.com/gpucores: 30

这是固定版本官方示例：数量 1、每卡显存预算 3000M、核心比例配置 30。核心比例不是端到端吞吐保证。sleep 只是保持容器存活，没有进行 CUDA 计算；镜像标签也不是不可变实验基线。

12 · API Server 与 Webhook：把请求送到正确入口

用户提交 Pod，API Server 执行准入流程。HAMi Webhook 调用设备类型的 MutateAdmission，识别资源；存在设备请求且配置了 SchedulerName 时，会设置 spec.schedulerName 并返回 patch。该分支还拒绝已设置 nodeName 的 Pod。它的产物是修改后的 Pod 对象，此时还没有挑选 GPU UUID。

因此要比较提交的 YAML 与保存下来的 Pod：Webhook 是否匹配、是否被调用、实际 schedulerName 是什么。不要只凭 YAML 没写 schedulerName，就断定走默认调度器。

13 · kube-scheduler 与 HAMi Extender：选节点，也选设备

本课采用 v2.7.0 Chart 的传统 Extender 路径。对应调度配置把 filter、bind 请求交给 HAMi Extender；kube-scheduler 是调度主流程，HAMi Extender 执行设备相关筛选与绑定逻辑。部署中“HAMi 调度器”常包含这些协作角色，不能把一个名字等同于一个函数。

Filter 读取请求和候选节点使用情况，调用 calcScore，排序后选出节点及设备集合。它把节点、时间与设备结果写入 Pod 注解，并更新内部 Pod/配额使用记录；注解 patch 失败有 delPod 回退分支。无可用节点时返回失败信息，节点总空闲显存的简单加和不能替代逐卡可满足性。

这些状态用于后续分配交接和避免重复预算分配；它们不等于应用进程已申请物理显存。追问：内部记录、API 注解、配额更新若只成功一部分，重试和重建如何收敛？这是后续读错误路径的入口，不能仅凭存在回退分支就宣称全链路事务一致。

14 · Bind：确定哪个节点负责接手

HAMi Bind 读取当前 Pod 与 Node，执行节点锁逻辑，写入 allocating 阶段和绑定时间，再调用 Kubernetes Pod Binding API。这里的产物是 Pod 与节点的绑定关系。绑定成功以后，节点侧 kubelet 才有依据继续该 Pod 的设备分配和启动。

所以“已选中 UUID”“已经绑定节点”“容器已启动”是三件事。绑定失败要看 API 错误和锁释放路径；已绑定但启动失败，排查重点转向节点侧，不应只盯调度分数。

15 · kubelet 与 Device Plugin：把决定变成启动配置

kubelet 经 Device Plugin 接口请求 Allocate。HAMi 的非 MIG 分支从待分配 Pod 注解读取下一组设备请求，检查数量是否匹配，并生成 ContainerAllocateResponse。它交付设备相关配置、CUDA_DEVICE_MEMORY_LIMIT_i、核心限制变量、共享缓存和库挂载等。

这里的 Allocate 是设备接入配置交付，不是替应用调用 cuMemAlloc。配置随后由 kubelet/容器运行时用于创建容器；插件本身不负责运行应用。默认控制分支还挂载 /etc/ld.so.preload，但 CUDA_DISABLE_CONTROL=true 会改变该分支。MIG、CDI 和不同设备列表策略须另按配置追踪。

UUID 用于关联同一物理设备；容器内索引 0 不一定是宿主机索引 0。若把索引当唯一身份，可能会拿另一张卡的指标证明当前 Pod。

16 · 到底怎样证明“拿到了”

把下面命令用于你有权限的目标集群；命名空间按实际替换。先只读检查，不需要修改工作负载。课程网页不会自动执行 kubectl。

kubectl -n default get pod gpu-pod -o yaml
kubectl -n default describe pod gpu-pod
kubectl -n default get events --field-selector involvedObject.name=gpu-pod --sort-by=.metadata.creationTimestamp
# 容器 Running 后检查配置，sleep 示例并不验证 CUDA
kubectl -n default exec gpu-pod -- sh -c 'env | sort | grep -E "CUDA_|NVIDIA_"; cat /etc/ld.so.preload'

先记录 Pod UID、时间、schedulerName、nodeName、设备注解与 Events，再关联对应调度器和节点插件日志。事件可能过期，同名 Pod 可能重建，必须核对 UID。环境变量和文件只证明配置可见；实际应用进程是否加载库、是否能执行 CUDA、预算是否生效，需要分别取证。

有 NVIDIA 环境时，使用固定镜像和驱动版本运行一个实际创建 CUDA context、分配、写入、同步、释放的程序，记录返回值与 GPU UUID。仓库 probe.c提供后续探针起点；当前未完成真实 GPU 编译与执行。第二课教你区分证据，第三课拆开运行时机制。

协议与节点资源的原始材料

协议按 kubelet v0.31.10（与本课 HAMi go.mod 的替换版本一致），提交 ae04b7f5088aa70f357f719cbefbf4a39cda6c95；Node 计数逻辑按 Kubernetes v1.31.10，提交 61183587c03f420214aac57f81dc0ecb43e1b0d6。它们是阅读基线，不声称当前集群部署了同一版本。

从主机到容器：按断点排查

  1. 主机 nvidia-smi 失败：先查驱动、设备与 NVML，尚未到 Kubernetes 协议。
  2. 主机正常而 Node 无资源：查插件发现/过滤结果、Register、ListAndWatch、kubelet 与 Node 状态发布。
  3. Node 有资源但 Pod Pending：核对实际 schedulerName、请求、已申请占用、节点约束与事件。
  4. 已绑定但容器 Waiting：查 Allocate 请求/响应、插件错误和运行时接入。
  5. Running 但 CUDA 失败：查具体 CUDA 错误、驱动/库兼容性、设备可见性和应用路径。
